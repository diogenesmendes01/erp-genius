1O que é um teste de front automatizado

É um roteiro de teste que o computador executa sozinho, num navegador de verdade, clicando e digitando como um usuário. No fim, ele diz o que passou e o que falhou.

Uma analogia

Pense numa receita de bolo. No teste manual, você lê a receita e faz o bolo. No teste automatizado, você escreve a receita num formato que um robô de cozinha entende. O robô faz o bolo do mesmo jeito todas as vezes. Quando algo dá errado, ele para e avisa: "no passo 6 a massa não cresceu".

No ERP Genius, a "receita" é algo assim: abrir /login, digitar o e-mail, digitar a senha, clicar em Entrar e conferir que o menu lateral tem os 9 itens do Vendedor, na ordem certa. Você já faz isso à mão no roteiro (documento 03). A automação repete esse roteiro em segundos, para os 14 usuários de teste.

Quatro palavras que você vai usar todo dia

Playwright

Ferramenta gratuita da Microsoft que controla o navegador por código. O projeto usa a versão 1.64.1. Os testes são escritos em TypeScript, uma forma de JavaScript com tipos.

Navegador headless

"Sem cabeça": o Chromium roda sem janela. Ele carrega, clica e digita, mas não desenha nada na sua tela. É mais rápido. Para ver o navegador, use o modo UI ou --headed.

Spec

Arquivo que termina em .spec.ts e guarda os testes de um módulo. Exemplo: e2e/login.spec.ts tem os testes de login. Cada teste dentro dele é um cenário.

Asserção (expect)

A conferência do teste: "espero que o título Acesso negado esteja visível". O Playwright espera até 10 segundos. Se não aparecer, o teste falha.

Manual e automatizado: cada um no seu papel

O manual é bom para fluxo novo, usabilidade, texto confuso e layout. O automatizado é bom para o que se repete igual: login, menu por papel, permissões e regressão a cada versão. Ele roda em segundos, mas não pega o que ninguém mandou conferir.

Onde isso entra na estratégia de testes

O documento 14 descreve uma pirâmide. Na base ficam os testes unitários e, no meio, os de integração com banco descartável (Vitest, do time de dev). No topo ficam os testes ponta a ponta (E2E), com Playwright. Quando o documento 14 foi escrito, o E2E era "futuro". Hoje ele existe na pasta e2e/, e essa pasta é sua.

A automação não substitui o roteiro manual

O primeiro ciclo continua manual. Automatize o que já passou no manual, se repete a cada versão e tem prioridade P1. Um teste automático só confere o que você mandou conferir.

As duas formas de "Acesso negado"

Redirecionamento

A página manda para /acesso-negado, que mostra o título "Acesso negado" e o link "Voltar ao início". Exemplos: /funil e /diario. No spec: mecanismo: "redirect".

Na própria página

A URL não muda e a tela mostra "Acesso negado" no lugar do conteúdo. Exemplos: /financeiro, /alunos e /empresas. No spec: mecanismo: "na-pagina".

O que está em test.fixme e por quê

test.fixme(...) marca um teste que o Playwright lista, mas não executa. No resultado ele aparece como pulado. O teste descreve o comportamento esperado, que hoje não acontece por causa de um bug conhecido ou de uma decisão que o PO ainda não tomou.

IDPapel e URLMotivo

PER-07dSECRETARIA em /empresasBug X2, o mesmo caso para a Secretaria

Quando a correção for publicada no UAT (ou o PO decidir), troque test.fixme por test e rode. Se o teste passar, ele vira proteção contra o bug voltar. Se a decisão for manter o comportamento atual, ajuste ou apague o caso.

Os nomes já usam os IDs do roteiro

Cada teste começa pelo ID do cenário em docs/qa/03-roteiro-testes-manuais.md. Quando um cenário vira vários testes, a letra final identifica a URL: PER-02a é /alunos, PER-02b é /configuracao/usuarios. O filtro -g, a planilha e a issue usam o mesmo ID.

3Preparar a máquina

Você vai instalar quatro coisas: Node, Git, VS Code e o navegador do Playwright. Faça uma vez por máquina. Reserve cerca de uma hora.

O que é o terminal

É a janela onde você digita comandos. No Windows, use o PowerShell ou o Git Bash (vem com o Git). No Mac, use o app Terminal. Dentro do VS Code, o terminal abre com Ctrl+` (Mac: Control+`). Digite o comando e aperte Enter.

  1. Instale o Node.js na versão 22

    O arquivo .nvmrc do projeto diz 22. É a versão usada pela CI. O mínimo técnico é 20.12, porque o playwright.config.ts usa process.loadEnvFile.

    Windows: no site nodejs.org, página de download, escolha a versão 22 e o instalador .msi. Avance com as opções padrão.

    Mac: no mesmo site, baixe o instalador .pkg da versão 22. Se você já usa o nvm, rode nvm install dentro da pasta do projeto: ele lê o .nvmrc.

    Feche e abra o terminal. Depois confira:

    node -v
    O que você deve ver

    v22. seguido de dois números, por exemplo v22.12.0. Se aparecer "não é reconhecido" ou "command not found", a instalação não terminou: reinstale e abra um terminal novo.

  2. Instale o Git

    Windows: baixe em git-scm.com e instale com as opções padrão. Ele traz o Git Bash.

    Mac: rode o comando abaixo. Se o Git não existir, o macOS oferece instalar as "ferramentas de linha de comando". Aceite.

    git --version
    O que você deve ver

    git version 2. seguido da versão, por exemplo git version 2.47.1.

  3. Instale o VS Code e a extensão do Playwright

    Baixe o VS Code em code.visualstudio.com. Abra a aba Extensões (Ctrl+Shift+X, no Mac Cmd+Shift+X), procure Playwright Test for VSCode, publicada pela Microsoft, e clique em Install.

    O que você deve ver

    Um ícone de tubo de ensaio (Testing) na barra da esquerda. Depois do passo 6, ele lista os testes da pasta e2e/ com um botão ▶ ao lado de cada um.

  4. Clone o repositório

    Você precisa do convite do GitHub (documento 01). No terminal, entre na pasta onde quer guardar o projeto e rode:

    git clone https://github.com/diogenesmendes01/erp-genius.git
cd erp-genius
    O que você deve ver

    Cloning into 'erp-genius'... e, no fim, o prompt de volta. Depois do cd, você está dentro da pasta erp-genius. Se o GitHub pedir login, entre com a sua conta convidada.

  5. Instale as dependências do projeto

    Este comando baixa as bibliotecas do projeto, inclusive o @playwright/test. Na regra do time, os agentes de desenvolvimento não rodam install: quem prepara o ambiente deles é o integrador. A sua máquina de QA é outra situação. Aqui você instala.

    npm install
    O que você deve ver

    Alguns minutos de espera e, no fim, uma linha como added 1234 packages in 3m (o número varia). Linhas npm warn são avisos e não impedem nada. Uma linha npm error impede: veja a seção 11.

  6. Baixe o navegador usado nos testes
    npx playwright install chromium
    O que você deve ver

    Barras de progresso de download e uma linha dizendo que o Chromium foi baixado para uma pasta ms-playwright. Para conferir a versão do Playwright:

    npx playwright --version
Version 1.64.1
Windows: "a execução de scripts foi desabilitada"

Se o PowerShell recusar o npx ou o npm com essa mensagem, troque por npx.cmd e npm.cmd (exemplo: npx.cmd playwright install chromium), ou use o terminal Git Bash. Não altere a política de segurança do Windows por conta própria: fale com o gestor.

4Configurar o acesso ao UAT

Os testes precisam de duas informações: a URL do UAT e as senhas dos usuários de teste. Elas ficam num arquivo só seu, o .env.e2e, que nunca vai para o GitHub.

  1. Copie o modelo

    Na pasta do projeto, rode o comando do seu terminal:

    # Git Bash ou Mac

cp .env.e2e.example .env.e2e
# PowerShell

Copy-Item .env.e2e.example .env.e2e
    O que você deve ver

    Nenhuma mensagem. No VS Code, o arquivo .env.e2e aparece na raiz do projeto, ao lado do playwright.config.ts, com o nome em cinza (cinza quer dizer "ignorado pelo Git").

  2. Preencha a URL do UAT

    Abra o .env.e2e no VS Code. Troque o exemplo pela URL que o gestor passou por canal privado. Ela começa com https:// e não tem barra no final.

    E2E_BASE_URL=<url-do-uat>
    O que você deve ver

    A URL abre no seu navegador comum e mostra a tela de login do ERP Genius. Confira também <url-do-uat>/api/health: deve mostrar ok: true e um sha.

  3. Preencha as senhas

    Para cada papel, preencha a linha E2E_PASSWORD_<PAPEL>= com a senha recebida. Sem espaço antes ou depois do =. Se a senha tiver espaço ou #, coloque-a entre aspas simples. As linhas E2E_EMAIL_<PAPEL> já vêm preenchidas com o padrão do seed: só mude se o gestor pedir.

    E2E_PASSWORD_VENDEDOR=<senha-do-vendedor>
E2E_PASSWORD_PROFESSOR=<senha-da-professora>
    O que você deve ver

    O arquivo salvo, com as 14 linhas de senha preenchidas. Pode começar com só algumas: os papéis sem senha são pulados no setup (seção 5).

  4. Confira que o arquivo está protegido
    git check-ignore -v .env.e2e
    O que você deve ver
    .gitignore:47:.env.e2e	.env.e2e

    Isso quer dizer que a linha 47 do .gitignore protege o arquivo. Se não aparecer nada, pare e avise o gestor antes de qualquer commit. Rode também git status: o .env.e2e não pode aparecer na lista.

5Rodar pela primeira vez

Agora você roda os 50 testes, aprende a ver o navegador trabalhando e a rodar só o que interessa.

O que acontece quando você roda

npm run test:e2e
→
Projeto setup: login de cada papel com senha
→
Sessões salvas em e2e/.auth/
→
Projeto chromium: specs em paralelo, já logados

O setup faz o login uma vez por papel, pela tela /login, e grava os cookies em e2e/.auth/<PAPEL>.json. Os testes de permissão reaproveitam esses arquivos e começam já logados. Isso economiza tempo e evita gastar tentativas de login. O setup roda sempre, mesmo quando você filtra os testes.

Rode tudo, sem janela

npm run test:e2e

Quando falta uma senha

O setup daquele papel aparece com - (pulado) e a razão: E2E_PASSWORD_ADMIN2 não definida: papel pulado no setup. Os outros papéis rodam normalmente. Os testes que usam o papel sem senha falham dizendo o que preencher:

[e2e] Senha do papel ADMIN2 não definida. Preencha E2E_PASSWORD_ADMIN2 no arquivo .env.e2e …
[e2e] Sessão de ADMIN2 não encontrada em …/e2e/.auth/ADMIN2.json. …

A primeira aparece no ACE-03 daquele papel. A segunda, nos testes que começam logados com ele. Já uma senha preenchida mas errada faz o setup falhar, e aí nenhum spec roda. Corrija a senha.

Outras formas de rodar

O -- separa as opções do npm das opções do Playwright. Tudo o que vem depois dele vai para o Playwright.

Cuidado com o ACE-07 e o bloqueio de login

O ACE-07 erra a senha do VEND-B (vendedor2) de propósito, uma vez por execução. Depois de 5 falhas em 15 minutos, o sistema bloqueia aquele e-mail, inclusive com a senha certa. Aí o setup do VENDEDOR2 falha e nenhum spec roda. Não rode a suíte inteira mais de 4 vezes em 15 minutos. Para repetir muito, filtre: -g "PER" ou o arquivo do seu spec.

6Ler o resultado

O terminal diz o que falhou. O relatório HTML e o trace dizem por quê. Print, vídeo e trace só são guardados para testes que falharam.

Relatório HTML

npx playwright show-report
O que você deve ver

O terminal mostra Serving HTML report at http://localhost:9323 e o navegador abre a lista de testes. No alto, filtros: Passed, Failed, Flaky, Skipped. Clique num teste para ver os passos, o erro, o print e o vídeo. Para fechar, volte ao terminal e aperte Ctrl+C.

Trace viewer, passo a passo

O trace é uma gravação completa do teste. Dá para "voltar no tempo" e ver a tela, o console e as requisições de cada momento. É a melhor evidência para o dev.

  1. Abra o teste que falhou no relatório HTML

    Filtre por Failed e clique no nome do teste.

  2. Clique na miniatura da seção Traces

    Fica no fim da página do teste. O Trace Viewer abre.

  3. Leia a lista de ações, à esquerda

    Cada linha é um comando: goto, fill, click, expect. A ação que falhou fica em vermelho.

  4. Clique na ação anterior à falha

    O centro mostra a tela naquele instante. As abas Before e After mostram antes e depois da ação. A faixa de miniaturas no alto também leva a qualquer momento.

  5. Leia as abas de baixo

    Errors: o esperado e o recebido. Console: erros do JavaScript da página. Network: as requisições e os códigos (um 500 aponta erro no servidor). Source: a linha do teste.

Também dá para abrir um trace direto pelo terminal:

npx playwright show-trace test-results/<pasta-do-teste>/trace.zip
O que você deve ver

A mesma janela do Trace Viewer, sem passar pelo relatório.

Para treinar sem esperar uma falha, force o trace num teste que passa. A opção --trace on existe no Playwright (confira em npx playwright test --help):

npm run test:e2e -- -g "PER-02a" --trace on
npx playwright show-report
O que você deve ver

O PER-02a passa e, no relatório, ganha a seção Traces. Abra e explore: goto /alunos, depois o expect do título "Acesso negado".

Vídeo e print

Ficam na pasta test-results/<nome-do-teste>-chromium/, ao lado do trace.zip: video.webm e test-failed-1.png. Também aparecem no relatório HTML. A pasta test-results/ é apagada no começo de cada execução: copie o que precisa antes de rodar de novo.

Anexar o trace numa issue

  1. Copie o trace.zip para fora do projeto

    Assim a próxima execução não apaga a evidência.

  2. Confira se não há dado sensível

    Abra o trace e olhe os prints e a aba Network. O trace guarda as requisições, inclusive o cookie de sessão do usuário de teste.

  3. Abra a issue pelo template Bug

7Anatomia de um teste

Vamos ler o ACE-07 real, de e2e/login.spec.ts, pedaço por pedaço. Ele cobre a primeira tentativa do cenário ACE-07 do roteiro: senha errada e e-mail inexistente. Algumas linhas foram quebradas para caber na página.

1. Importar as ferramentas

import { test, expect, login, menuPrincipal } from "./fixtures/auth";
import { emailDe, PAPEIS, type PapelE2E } from "./fixtures/usuarios";

const MENSAGEM_LOGIN_RECUSADO = "E-mail ou senha incorretos.";

import traz funções de outros arquivos. O test e o expect vêm de ./fixtures/auth, e não de @playwright/test: é essa versão que tem a opção papel. A constante guarda o texto esperado num lugar só.

2. Declarar o teste

test.describe("Login", () => {
  test(
    "ACE-07 senha errada e e-mail inexistente mostram a mesma mensagem e continuam em /login",
    async ({ page }) => {

test.describe agrupa testes com um título ("Login"). test(nome, função) cria um teste. O nome começa pelo ID. async ({ page }) recebe a aba do navegador, já aberta e sem sessão, porque este bloco não usa test.use({ papel }).

3. Agir na tela

      await page.goto("/login");
      await page.locator('input[name="email"]').fill(emailDe("VENDEDOR2"));
      await page.locator('input[name="senha"]').fill("senha-errada-e2e");
      await page.getByRole("button", { name: "Entrar" }).click();

await quer dizer "espere esta ação terminar antes da próxima". page.goto("/login") abre a URL; o começo (E2E_BASE_URL) vem da configuração. locator(...) encontra um elemento. fill digita, click clica. O e-mail é o do VEND-B, e a senha é inválida de propósito.

4. Conferir o resultado

      await expect(page.getByText(MENSAGEM_LOGIN_RECUSADO)).toBeVisible();
      await expect(page).toHaveURL(/\/login/);

expect(...) é a asserção. toBeVisible() espera até 10 s o texto aparecer. toHaveURL(/\/login/) confere que a URL contém /login. O que está entre barras é uma expressão regular, um padrão de texto; a \/ é uma barra escrita de forma "escapada".

5. Repetir com um e-mail que não existe

      await page.locator('input[name="email"]').fill("nao-existe-e2e@genius.com");
      // … mesma senha, mesmo clique em Entrar e os mesmos dois expect …

    },
  );
});

A mensagem tem de ser a mesma. Se fosse diferente, um invasor descobriria quais e-mails existem no sistema.

O teste usa getByText, e não getByRole("alert"), porque o Next.js também coloca na página um anunciador de rota com role="alert". Haveria dois "alertas". Quando você escolher um seletor, deixe um comentário se o motivo não for óbvio.

9Boas práticas neste projeto

Regras curtas que evitam teste frágil, dado perdido no UAT e risco de mensagem real.

ID do roteiro no nome

O nome começa pelo ID (CRM-04 …) e segue com uma frase do que se espera. Assim o filtro -g, a planilha e a issue falam a mesma língua.

Um spec por módulo

login.spec.ts, permissoes.spec.ts, crm.spec.ts e depois matricula.spec.ts, financeiro.spec.ts, alunos.spec.ts. Não misture módulos num arquivo.

Testes independentes

Os testes rodam em paralelo e em qualquer ordem. Nenhum teste pode depender de outro ter rodado antes, nem de dado criado por outro.

Cada teste cria o que precisa

Se o teste precisa de uma oportunidade, ele mesmo cria, com um nome único, e confere em cima dela.

Seletores: do mais forte ao mais frágil

OrdemSeletorQuando usar
1getByRole("button", { name: "Entrar" })Sempre que der: botões, links, títulos, abas, diálogos.
2getByLabel("Responsável")Campos de formulário com rótulo.
3getByText("E-mail ou senha incorretos.")Mensagens e textos soltos.
4locator('input[name="email"]')Só quando não há papel nem rótulo.
Evitelocator(".flex > div:nth-child(3) button")Classes CSS e posições mudam a cada ajuste de layout. XPath também.

Dados criados pelo teste

O roteiro pede que todo registro comece com QA. O README pede que a automação seja identificável. Use o prefixo QA-E2E-, que atende os dois, e um carimbo de tempo para o nome não repetir:

const nome = `QA-E2E-OPORT-${Date.now()}`;

Telefones só fictícios, no formato do roteiro (+506 8888 01xx). Como o CRM avisa quando um telefone já existe (CRM-03), peça ao gestor uma faixa reservada para a automação antes de criar oportunidades em massa.

Faça

  • Espere com expect(...). Ele já espera até 10 s o elemento aparecer.
  • Escreva o bug conhecido com o comportamento esperado e marque com test.fixme, com um comentário citando o X ou o R.
  • Comentários e nomes em português.
  • Rode o seu teste novo pelo menos três vezes seguidas antes do PR. Se falhar uma vez sem motivo, ele está instável.
  • Quando um texto da tela mudar, confirme com o roteiro ou com o dev se a mudança é intencional antes de mudar o teste.

Não faça

  • page.waitForTimeout(...) ("espere 3 segundos"). Deixa o teste lento e ainda falha quando o UAT demora mais.
  • test.only esquecido no commit. Ele faz só aquele teste rodar.
  • Alterar configuração global do UAT (Operação, Países, Catálogo, Preços, Usuários) num teste automático sem combinar. Isso muda o ciclo manual dos colegas.
  • Mexer em vitest.config.ts ou nos testes de src/. São do time de dev.
Nunca, em hipótese alguma

Nunca rode contra produção. E2E_BASE_URL é sempre o UAT. Nunca escaneie o QR do WhatsApp, nem à mão nem num teste, e nunca automatize o botão "Conectar" de um número (CFG-30). Algumas ações da Inbox chamam o motor do WhatsApp direto, sem a trava WHATSAPP_LIVE. Com um celular pareado, elas mandariam mensagem de verdade (bug X15). Nunca use e-mail, telefone ou documento de pessoa real.

    O Git mostra um link para criar o pull request. Abra o link, confira que a base é main e preencha a descrição.

O que escrever na descrição do PR

Os IDs do roteiro cobertos (total ou parcial); o comando, o resultado (ex.: 15 passed), a data e o sha de /api/health; os test.fixme com o X ou R de cada um; e os dados que o teste cria no UAT. Nunca senha, URL do UAT ou trace com dado sensível.

A CI não roda os testes E2E

A CI do repositório (.github/workflows/ci.yml) roda quatro coisas em cada PR: typecheck, lint, testes unitários (em dois fusos) e build. Ela não tem o .env.e2e nem acesso ao UAT, e não executa o Playwright. CI verde não quer dizer que o seu teste passa: quem revisa confia no resultado que você colou no PR. Mas a CI confere os seus arquivos: o TypeScript inclui a pasta e2e/, e o lint tem um teto de 40 avisos no projeto todo, que um aviso novo seu pode estourar.

13Glossário e checklists

Glossário

Asserção
A conferência de um teste, escrita com expect(...). Se não se confirma no tempo, o teste falha.
baseURL
O começo de todas as URLs, vindo de E2E_BASE_URL. Por isso o teste escreve só "/funil".
Codegen
Gravador do Playwright. Abre o navegador e escreve o código enquanto você clica.
Fixture
Algo que o Playwright prepara para o teste antes de ele começar: a page, a sessão do papel.
Flaky
Teste instável: às vezes passa, às vezes falha, sem mudança no sistema.
Locator
A "mira" que encontra um elemento na tela, como getByRole(...).
Papel
O usuário de teste que o teste usa: VENDEDOR, PROFESSOR. Configurado com test.use({ papel }).
Rate limit
Limite de tentativas. No login: 5 falhas em 15 minutos por e-mail.
Sessão (storageState)
Os cookies de um login, salvos em e2e/.auth/<PAPEL>.json.
test.fixme
Teste listado e não executado, para bug conhecido ou decisão pendente.
Trace
Gravação completa de um teste (trace.zip), aberta no Trace Viewer.
UAT
Ambiente de homologação, onde o QA testa. Nunca é produção.

Checklist antes de abrir o PR

  • O nome de cada teste começa pelo ID do roteiro, e nenhum teste depende de outro.
  • Dados criados começam com QA-E2E- e usam só telefones e e-mails fictícios.
  • Nenhuma senha, URL do UAT, test.only, waitForTimeout, QR ou "Conectar" de número no código.
  • Três execuções seguidas com ✓, npx eslint e2e sem saída e nada sublinhado em vermelho.
  • git status mostra só arquivos de e2e/.
  • A descrição do PR tem IDs, comando, resultado, data e sha do UAT.
